# Server instructions

## Project overview

- ASP.NET Core vertical-slice API with MediatR-free CQRS. `Program.cs` owns routing/middleware; `DependencyInjection.cs` owns assembly scanning and handler decorators.
- Business routes use `/api/v1`; health is `/api/health`. The server also hosts the built Vue SPA.

## Structure

Paths are relative to this project. `{Domain}` and `{UseCase}` are placement patterns, not literal directories.

| Location | Responsibility / what belongs here |
| --- | --- |
| `Program.cs` | Host composition, middleware order, API grouping, and SPA fallback; not use-case business logic. |
| `DependencyInjection.cs` | Service lifetimes, assembly scanning, and decorator composition; not application workflows. |
| `Features/{Domain}/{UseCase}/` | One operation's endpoint, request/response, command/query, handler, and validator. Keep the operation's behavior together rather than splitting it into global controller/service folders. |
| `Features/{Domain}/` | Domain-owned entities, EF mappings, errors, cache keys, permission constants/catalogs, and events shared by that domain's use cases. Do not turn these into cross-feature dependencies. |
| `Features/Identity/` | Credential/token lifecycle and the caller's own session; user-record queries belong in `Features/Users/`. |
| `Authentication/` | Technical identity mechanisms: token creation/validation, password hashing, and caller context; not credential endpoints or business permissions. |
| `Authorization/` | Permission resolution/enforcement and role/catalog seeding. Feature-specific permission definitions belong to their feature. |
| `Common/` | Domain-neutral contracts and cross-cutting behavior needed across features, including shared errors. Must not depend on any feature. |
| `Database/ApplicationDbContext.cs` | Persistence orchestration and shared identity DbSets; access feature entities with `Set<T>()` instead of adding feature dependencies here. |
| `Database/Entities/Identity/` | Minimal identity/access entities consumed by infrastructure. Feature-specific profile data belongs in a feature-owned entity keyed by user ID. |
| `Database/Configurations/` | Mappings for shared identity/access entities; feature-owned mappings stay with their entity under `Features/`. |
| `Database/Migrations/` | Versioned schema changes and generated model snapshot; not runtime application logic. |
| `Integrations/` | Technical adapters and configuration for external capabilities such as cache/email. Keep provider-specific code out of endpoints and business handlers. |
| `Properties/launchSettings.json` | Developer launch profiles, URLs, and environment selection; not production deployment settings. |
| `appsettings*.json` | Runtime configuration defaults/overrides; supply production secrets externally. |
| `wwwroot/` | Generated SPA assets for hosting; never put hand-maintained client source here. |
| `Dockerfile` | Image build/publish/runtime stages; service topology belongs in root Compose configuration. |

## Build and test commands

- Commands below run from the repo root. Start PostgreSQL: `docker compose up -d postgres`.
- Development database settings are machine-specific. For Compose, run:
  `ConnectionStrings__Database='Host=localhost;Port=5432;Database=aspnetvue;Username=postgres;Password=postgres' dotnet run --project src/AspNetVue.Server`.
- API uses port 5000. SpaProxy is configured to launch `bun run dev` on port 5173; avoid duplicate Vite instances.
- Build: `dotnet build AspNetVue.slnx`.
- NuGet versions belong in root `Directory.Packages.props`, not individual `.csproj` files.
- Docker-free checks: `dotnet test tests/AspNetVue.Server.UnitTests` and `dotnet test tests/AspNetVue.Server.ArchitectureTests`.
- Full suite: `dotnet test AspNetVue.slnx` (integration tests require Docker).

## Code style guidelines

- Follow root `.editorconfig`: usings outside namespaces, explicit types except where the type is apparent. Style/analyzer violations fail builds.
- Add `// <auto-generated />` to generated migration `.cs` files to avoid the enforced file-scoped-namespace error.

## C# Conventions

- Use top-level statements for the application entrypoint, nullable reference types (enabled centrally), and file-scoped namespaces for ordinary source files.
- Use `PascalCase` for types, methods, properties, and public members; `camelCase` for local variables and parameters.
- Keep one top-level type per file, with the filename matching the type. Tightly coupled nested/private types may remain together; generated migrations and the partial `Program` test entrypoint retain their generated/hosting structure.
- Use `async`/`await` for I/O-bound work; do not block with `.Result` or `.Wait()`.
- Prefer constructor injection over static/global service instances; use the existing registrations in `DependencyInjection.cs`.
- Keep `System` usings first and do not separate import groups with blank lines, per `.editorconfig`. Internal namespaces use `AspNetVue.Server.*`.

## Architecture conventions

- Handlers and `IEndpoint` implementations are assembly-scanned and must be sealed. Return `Result`/`Result<T>` from handlers and map failures with `CustomResults.Problem` at endpoints.
- Keep use-case prefixes on types, such as `CreateTodoCommand`, `CreateTodoHandler`, and `CreateTodoEndpoint`, under `Features/{Domain}/{UseCase}`.
- Features cannot reference each other; `Authentication`, `Authorization`, `Database`, and `Common` cannot reference features (see root `ARCHITECTURE.md` §§1, 10–11).
- Feature entities/configurations stay in their feature; use `context.Set<T>()`, not feature `DbSet` properties in `ApplicationDbContext`. Preserve table names explicitly. Shared identity entities belong in `Database/Entities/Identity`.
- Business routes are relative to `/api/v1` and use `.MapToApiVersion(1)`; health stays `/api/health`. Preserve API JSON 404s before the SPA fallback. Update README, OpenAPI tags, and integration tests for route changes.

## Testing instructions

- Focus a handler: `dotnet test tests/AspNetVue.Server.UnitTests --filter 'FullyQualifiedName~CreateTodoHandlerTests'`.
- Integration suite: `dotnet test tests/AspNetVue.Server.IntegrationTests`. Testcontainers creates its own database and needs Docker plus access to pull `postgres:17`, not a running Compose database.
- Routing-only checks need no Docker: `dotnet test tests/AspNetVue.Server.IntegrationTests --filter 'FullyQualifiedName~ApiVersioningTests'`. A caught startup database error may be logged.
- Reuse `tests/AspNetVue.Server.UnitTests/Abstractions/BaseHandlerTest.cs` for unique InMemory databases and real HybridCache instances. Use PostgreSQL integration tests for relational/migration behavior; InMemory does not exercise PostgreSQL.
- Add new features to the hard-coded isolation list in `tests/AspNetVue.Server.ArchitectureTests/Layers/LayerTests.cs`.

## Security considerations

- Enforce feature-owned permission constants/catalogs with endpoint `.HasPermission(...)`, not handler role checks. JWTs contain identity, not permissions; invalidate `IPermissionProvider` cache after role/permission changes. Permission lookup failures must deny access.
- `AuthorizationDataInitializer` migrates only in Development and seeds on every start; failures are caught. A running API does not prove initialization succeeded. Production requires separate migrations and database/JWT configuration; do not reuse the development JWT secret.
- JWT settings and relaxed rate limits in `IntegrationTestWebAppFactory.cs` are test-only overrides. Preserve real permission enforcement in `tests/AspNetVue.Server.IntegrationTests/Authorization/AuthorizationTests.cs`.
